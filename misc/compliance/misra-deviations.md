# MISRA C++ — Deviations

Register of accepted deviations from MISRA C++:2023 (see `misra-cpp.md`). Each entry records the
guideline, its category, the affected code and the justification. A deviation against a Required
guideline is only valid once formally approved; Advisory deviations are recorded for traceability.

| ID | Guideline | Category | Location | Justification |
| --- | --- | --- | --- | --- |
| DEV-001 | Rule 16.6.1 — Symmetrical operators should only be implemented as non-member functions | Advisory | `include/dojio/error.hpp:26`, `include/dojio/result.hpp:22,27`, `include/dojio/fd.hpp:23`, `include/dojio/operation_id.hpp:13` | The symmetrical `operator==` is defaulted as a member. A defaulted comparison is inherently symmetric (the compiler generates `a == b` from the two operands) and has no asymmetric overload-resolution or conversion pitfalls, so rewriting the operators as hidden friends adds no safety. |
| DEV-002 | Rule 19.6.1 — The `#pragma` directive and the `_Pragma` operator should not be used | Advisory | All `include/dojio/*.hpp` (17 headers) | The project mandates `#pragma once` (see `AGENTS.md`); it is a portable include-once precaution that satisfies Rule 19.2.1 and avoids the guard-name/ODR maintenance burden. |
| DEV-003 | Rule 21.6.3 — Advanced memory management shall not be used | Required | `include/dojio/dojio_memory.hpp` (BoxPtr), `include/dojio/ring_engine.hpp`, `src/dojio/ring.hpp`, `src/dojio/ring.cpp` | The engine uses `std::pmr` (`polymorphic_allocator`, `memory_resource`, `unsynchronized_pool_resource`) so the submission/completion hot path performs no heap allocation: `Action` objects are carved from the ring's per-`RingEngine` pool (`IoUring::action_pool()`), and `BoxPtr` records the allocator/size/alignment to return the exact storage on derived-to-base destruction. The pending set itself is a `detail::SlotTable` over a plain `std::vector`, so it no longer allocates per operation either. Allocations remain automatically managed (RAII), so Rule 21.6.2 is unaffected. Replacing `std::pmr` with fixed arenas is possible but is a redesign; the residual risk is bounded to a not-thread-safe, pre-sized internal pool. |
| DEV-004 | Rule 24.5.2 — The C++ Standard Library functions `memcpy`, `memmove`, `memcmp` and `memchr` from `<cstring>` shall not be used | Required | `src/dojio/socket.cpp` (`bind`, `connect`), `src/dojio/ops.cpp` (`statx_to_stat`) | Used only to move the object representation of trivially-copyable kernel ABI types: a `sockaddr_in`/`sockaddr_in6` into the operation buffer (whose storage is `alignas(std::max_align_t)`, `static_assert`ed against the address types so the later `sockaddr` view is aligned), and a kernel-written `struct statx` byte buffer into a real `struct statx` value. Both extents are compile-time bounds, the regions never overlap, and `std::bit_cast`/`std::copy` alternatives were rejected as less readable for the same byte transfer. |
| DEV-005 | Rule 21.2.2 — The string handling functions from `<cstring>`, `<cstdlib>`, `<cwchar>` and `<cinttypes>` shall not be used | Required | `src/dojio/ring.cpp` (`reserve_sqe`) | `std::memset` zeroes an `io_uring_sqe` before its fields are filled. The write is bounded by `sizeof(io_uring_sqe)`, the struct is trivially copyable, and value-initialization was rejected because the kernel SQE is a union-bearing UAPI struct where an explicit zeroing call is clearer. |
| DEV-006 | Rule 0.0.1 — A function shall not contain unreachable statements | Required | `src/dojio/ring_engine_stub.cpp` (`cancel`, `process`, `poll`, `supports_op`, `capabilities`, `count_operations`, `ring_fd`, `sqpoll_enabled`, `sqpoll_poll_time`) | The non-Linux stub keeps an explicit `return` after the `[[noreturn]]` `unreachable()` call. The returns are unreachable; they exist only to make the non-void control flow explicit for toolchains/analysers that do not model `[[noreturn]]`. |
| DEV-007 | Rule 21.6.1 — Dynamic memory should not be used | Advisory | `src/dojio/ring.cpp`, `src/dojio/ring_engine.cpp`, `src/dojio/memory_pool.cpp`, `src/demos/tcp_hello.cpp`, and the standard containers used throughout | Dynamic memory is used for the long-lived engine/ring/pool objects (`std::unique_ptr` wrapping `new`) and for the standard-library containers (`std::vector`, the `detail::SlotTable` slots, `std::make_shared` in the demo). Every allocation is owned by an RAII smart pointer or container, so Rule 21.6.2 is satisfied; Rule 21.6.1 is Advisory (and the standard acknowledges applications may need dynamic memory, subject to justification), and owning kernel/OS resources with automatic lifetime is the library's purpose. |
| DEV-009 | Rule 6.7.1 — Local variables shall not have static or thread storage duration | Required | `src/dojio/memory_pool.cpp` (`page_size`) | The page size is constant for the lifetime of the process: reading it once from `sysconf(3)` and caching it in an immutable function-local `static` (C++11 thread-safe initialisation) keeps the `RegisteredMemoryPool` construction free of a repeated `sysconf` call and removes a per-pool data member. The cached value is `const`, trivially copyable and never mutated. |

> **Resolved:** DEV-008 was removed when `src/dojio/version.cpp` was deleted. Opcode availability is no
> longer cached from `uname(2)`; it is discovered once per ring with `IORING_REGISTER_PROBE` and stored
> in the `IoUring` instance (`supported_ops_`), so no function-local `static` remains.
